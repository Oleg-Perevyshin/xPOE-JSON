# 🧪 Тесты xPOE-JSON

## 📋 Обзор

Один файл — `test_json.c`. Без стороннего тестового фреймворка: `test_assert.h` — три макроса
(`TEST_CHECK`, `TEST_SECTION`, `TEST_REPORT`), ничего больше. Компилируется как обычный C-исполняемый
файл (`tests/CMakeLists.txt`), результат — код возврата `0`/`1` плюс текстовый отчёт в stderr.

Для CTest это **один** тест — `add_test(NAME test_json COMMAND test_json)`. CTest видит только общий
pass/fail всего бинарника; деление на смысловые проверки существует только внутри — как текстовые
заголовки в логе (см. «Подробный вывод» ниже), не как отдельные CTest-тесты.

## 🧱 Структура файла

18 функций `test_*`, вызываемых из `main()` по порядку. Каждая может содержать несколько вызовов
`TEST_SECTION(...)` — это не отдельные тесты, а подписи внутри общего лога, чтобы при падении сразу
было видно, какая смысловая часть отказала.

| Функция | Что покрывает |
|---|---|
| `test_basic_types` | Создание и печать всех примитивных типов (`null`/`bool`/`number`/`string`/`array`/`object`) |
| `test_number_print` | Сериализация чисел: обычные значения, `-0.0`, насыщение вне `long long`, `nan`/`inf`, перенос разряда при округлении |
| `test_number_parse` | Разбор чисел (целые/дробные/экспонента) + независимость от locale |
| `test_parse_literals` | Разбор `null`/`true`/`false` |
| `test_string_escapes` | Escape-последовательности в обе стороны: разбор (`\n\t\"\\/ \b\f\r \uXXXX`, битая hex-цифра) и сериализация (кавычка/бэкслеш/control-байт на выходе) |
| `test_utf8` | Сырые многобайтовые символы (кириллица/иероглифы/эмодзи) насквозь, `\uXXXX` на 2 и 3 байта, известное ограничение — суррогатные пары не собираются |
| `test_parse_reject_invalid` | Некорректный JSON отклоняется, арена откатывается |
| `test_depth_limit` | Лимит `xPOE_JSON_MAX_DEPTH` — отдельно для массивов и объектов |
| `test_mixed_nesting_and_empty_containers` | Пустые контейнеры, массив объектов, объект массивов |
| `test_large_array` | Массив на 5000 элементов — индексация, round-trip |
| `test_resource_limits` | Нехватка памяти: разбор в маленький буфер, откат `Create*`/`Add*`-хелперов, `JSON_BeginObject` на буфере меньше минимума, усечение `JSON_Print` |
| `test_whitespace_variety` | Пробелы/табы/переносы строк вокруг токенов |
| `test_roundtrip` | Полный цикл создание → печать → разбор → сверка, включая отсутствующий ключ |
| `test_duplicate` | `JSON_Duplicate` — глубокая независимая копия (число, строка, вложенный объект/массив) |
| `test_container_helpers_direct` | Прямые вызовы `JSON_AddObjectToObject`/`JSON_AddObjectToArray`/`JSON_AddItemToObject` (не только через `JSON_Parse` текста) |
| `test_sort_object` | `JSON_SortObject` — 3001 ключ по убыванию (без переполнения стека) + 1000 ключей в перемешанном порядке (все 4 ветки слияния) |
| `test_clear_context` | `JSON_ClearContext` — повторное использование арены |
| `test_invalid_args` | Защита от `NULL`/некорректных аргументов + защитная ветка `JSON_Print` на испорченный `type` |

## 🚀 Запуск

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build --output-on-failure
```

В VS Code — через расширение **CMake Tools** (`ms-vscode.cmake-tools`, рекомендовано в
`.vscode/extensions.json`): `Cmd/Ctrl+Shift+P` → `CMake: Configure` (первый раз попросит выбрать
компилятор — Kit), затем панель **Testing** в Activity Bar (иконка колбы) или `Testing: Focus on Test
Explorer View` из палитры команд, если иконка не видна сразу.

## 🔍 Подробный вывод

По умолчанию `ctest` печатает вывод теста только при провале (`--output-on-failure`). Чтобы видеть
все `-- секция ...` и итоговое `N/N checks passed` при каждом запуске, даже при полном успехе:

```bash
ctest --test-dir build -V
```

В `.vscode/settings.json` уже прописано `"cmake.ctestArgs": ["-V"]` — расширение CMake Tools всегда
покажет подробный лог, не только при падении.

## 📊 Покрытие кода

```bash
mkdir build_cov && cd build_cov
gcc -std=c11 --coverage -O0 -g -I.. ../poe_json.c ../tests/test_json.c -I../tests -o test_cov -lm
./test_cov
lcov --capture --directory . --output-file coverage.info --rc branch_coverage=1 \
     --ignore-errors unsupported,inconsistent
lcov --remove coverage.info '*/tests/*' --output-file coverage.lib.info --rc branch_coverage=1 \
     --ignore-errors inconsistent,unused
lcov --list coverage.lib.info --rc branch_coverage=1 --ignore-errors inconsistent
```

(`lcov`/`genhtml` — `brew install lcov`, если их нет)

Текущий результат для `poe_json.c`: **100% строк, 100% функций**. Branch coverage — 78.2%: это отдельная,
более строгая метрика (обе стороны каждого условия), и остаток там — в основном defensive-проверки
(`if(!ptr)`) на внутренних `static`-хелперах, которые изнутри библиотеки вызываются только с валидными
указателями; недостижимая сторона условия проверяется лишь белым ящиком (вызвать `static`-функцию
напрямую с намеренно плохим аргументом), что не тестирует поведение публичного API. 100% branch/MC-DC —
это по сути другой, кратно более дорогой уровень тестирования (типичный для DO-178C), и для этой
библиотеки избыточен.

### Осознанно принятые пробелы

| Место | Почему не покрыто | Почему это нормально |
|---|---|---|
| `JSON_BeginObject`, ветка `if(!ctx->root)` | Помечена `LCOV_EXCL_START/STOP` | Доказанно недостижима: `JSON_InitContext` требует запас `+64` байта сверх `sizeof(JSON_Context)`, а `sizeof(JSON)` — 56 байт на большинстве платформ, так что создание первого узла после успешной инициализации провалиться не может. Ветка — защита на случай будущего роста структуры `JSON` |
| `list_merge_sort`, 2 из 4 веток слияния | Требуют конкретной формы входных данных | Изначально не хватало — тест с *строго убывающей* вставкой ключей оказался вырожденным случаем (левый `RUN` слияния всегда целиком больше правого). Закрыто добавлением `test_sort_object`'s второй секции — перемешанный порядок через мультипликативную перестановку `(i*601) % N` |

Второй пробел уже закрыт (было исправлено при доведении покрытия до 100% построчного), первый —
осознанно принят и не будет закрыт без изменения инвариантов аллокатора.

## ⚠️ Подводные камни при правке тестов

- **`\x01d` в C-строке — это НЕ байт `0x01` + `'d'`.** У escape `\x` нет фиксированной ширины, он жадно
  поглощает все идущие подряд шестнадцатеричные цифры — `'d'` тоже валидная hex-цифра, поэтому
  `\x01d` парсится компилятором как один байт `0x1D`. Для `0x01` за которым идёт буква/цифра — используйте
  восьмеричный `\001` (эта форма всегда ровно 1–3 цифры, `'d'` в неё не попадёт).
- **`s_buf`/`s_buf2`** — общие глобальные буферы на 1 МБ, переиспользуются между функциями через
  `fresh_ctx()`/`JSON_InitContext`/`JSON_BeginObject`. Переинициализация одного и того же буфера уничтожает
  данные предыдущего контекста на нём — безопасно только после того, как нужные данные уже скопированы
  оттуда (например, в `s_out`) или контекст больше не нужен. Если тесту нужны две независимые живые
  структуры одновременно — используйте разные буферы (`s_buf` и `s_buf2`) или срез одного буфера
  пополам, как в `test_roundtrip`.
- **`TEST_SECTION` можно вызывать несколько раз в одной функции** — это не создаёт отдельный тест для
  CTest, только подпись в логе; группировать несколько связанных проверок в одну функцию с несколькими
  секциями — нормально и осознанно используется в этом файле (см. «Структура файла» выше).
- Новые проверки, трогающие сериализацию/разбор чисел или указатели, стоит дополнительно прогонять под
  ASan/UBSan — coverage не ловит UB, только «эта строка выполнилась»:
  ```bash
  cmake -S . -B build_san -DCMAKE_C_COMPILER=clang \
        -DCMAKE_C_FLAGS="-fsanitize=address,undefined -fno-sanitize-recover=all" \
        -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
  cmake --build build_san && ./build_san/tests/test_json
  ```
